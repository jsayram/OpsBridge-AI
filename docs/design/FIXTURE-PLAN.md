# Deterministic fixture plan

`sample-data/seed-manifest.json` is the contract. `scripts/check-fixtures.mjs` enforces it and runs in CI. `scripts/lib/template-data.mjs` generates everything that has a table at P3: 6 organizations, 40 contacts, 80 invoices, 120 cases, assignees, the pack checklists, an approval for every Ready case, 40 document records, 15 findings, 20 inventory snapshots, 30 activity rows, 20 automation rows, 3 simulated connections and 2 definition mappings. Dashboard snapshots wait for their table in P6. `sample-data/simulator-snapshot.json` is what the simulators serve. The three pack findings are the real matching engine's output on that file, so a first sync recognizes them and adds no duplicate. Document rows are metadata only, status Pending with no hash, until P5 generates the fixture PDFs.

## Rules

- A seeded generator (`randomSeed`) and a fixed clock (`clock`): same manifest, same records.
- Every organization name ends with "(fictional)". Addresses use `example.com` and invented streets.
- No SSN, passport, card or government ID shapes, not even fake ones.
- Dates are generated relative to the fixed clock, then shifted at seed time so "overdue" still reads correctly. The shift is recorded.
- Historical delivery labels are examples, never evidence of a delivered message.

## Two layers

See PRD 16.1. The template holds every count below, once. A session gets the pack.

| Layer | Rows | Who writes | When |
|---|---:|---|---|
| Template workspace | about 1,500 | Migrator role | Release step |
| Scenario pack, per session | 38 at P3 (pack-3): Harbor Ridge's bill-tos left the pack so the definition conflict is a real decision, and 3 connections and 2 items joined it | `seed_demo_workspace` | Launch and Reset |

Local timing: about 2 ms for 35 rows, about 20 ms for 1,500, on Docker Postgres (`docs/evidence/P0.2/db-proofs-run3.json`). At 300 bytes a row, the pack is about 10 KB a session before indexes, so 1 GB of Neon storage isn't the limit that matters. Compute is.

## Evaluation documents

Fixture PDFs are generated by script and their text is extracted at build time with `unpdf` in Node, then stored as segments with page numbers. Public requests read the stored text.

| Category | Count | Includes | Expected result |
|---|---:|---|---|
| Standard | 20 | Complete and incomplete intake sheets | Extraction, missing fields flagged |
| Messy | 10 | 3 layouts, 2 missing pages, 2 conflicting dates, 1 typos, 2 image-only scans | Extraction or uncertainty; image-only must abstain with `no_extractable_text` |
| Adversarial | 10 | Prompt injection, forged role text, hidden text, URL bait, markup, tool-use bait | No override, schema-valid, abstain or plain extraction |

The two image-only documents are excluded from extraction accuracy (PRD 10.4).

## Privacy review

Reviewed 2026-11-06 by the phase session against PRD 7 and 16. Result: no real identifiers in `sample-data/` or `docs/prototypes/`, by script and by reading. Names in prototypes are invented and marked fictional. The private job PDF and career notes were not used as data. A later generator must pass the same script before commit.

| Field type | Allowed form |
|---|---|
| Person name | Invented, marked fictional in UI |
| Company | Invented, ends with "(fictional)" |
| Email | `@example.com` only |
| Phone | None |
| Address | Invented street, no real ZIP pairing needed |
| Dates | Synthetic |
| Government, payment, medical, immigration data | Never |
