## Outcome and scope

Done locally. A manager or the owner accepts, edits or rejects a suggestion. Reject changes nothing on the case. Accept can carry the case version the reviewer saw; the checklist changes the rules allow are then committed through `updateChecklistItem`, the same version-checked command a person uses, in one transaction with the decision, and each changed item's evidence reference points back at the review and the cited segments. A stale case version or review version rolls everything back. Edits are stored beside the immutable suggestion, limited to schema fields and checked by the same field rules. No AI event type exists and the suggestion never reaches the outbox.

## Independent review follow-up

- **Unpreviewed changes (Medium, fixed).** An accept that applies changes must now send `expectApply`, the exact list the reviewer was shown; if the server's list differs, nothing changes (`apply_changed`). Edits go through a read-only preview, `POST /api/v1/ai-reviews/{id}/preview`, and the UI shows the new list before "Accept with edits".
- **Edits on an abstention (Medium, fixed).** The server refuses `accept_with_edits` and preview on an abstained review (`invalid_edit`).
- **Retry (Low, fixed).** Retry checks the document is ready and no other review is running, and refuses a failed live row (`live_retry_is_new_request`) so its record of the paid attempt stays.
- New tests: another client's document, abstained edits, accept without a case version, a Ready case refusing a document, `apply_changed`, retry of a live row.
