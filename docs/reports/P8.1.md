## The WebKit "New case" intermittent: explained

P7.4 saw a click on **New case** sometimes fail to open the form in WebKit. The new regression test holds back the `/assignees` response, measures the button, then lets the response through: the button moved **142 px to the right** (x 1127 to 1269) because the assignee filter widened to fit "Rae Lindqvist, observer (fictional)". A click aimed at the old spot lands on empty space, which in WebKit focuses `main`. That matches the P7 failure snapshot, where `main` had focus and the form never opened. With a fixed width, the button doesn't move. The test fails without the fix and passes with it. After the fix: full WebKit run 113 passed with no retry needed, and five more WebKit desktop repeats of every New case test passed. Real Safari still needs checking (P7 list item 8).

## A case-list crash after a search: found and fixed

The first full Chromium run showed the error boundary once, after a search on the Pixel 7 profile; a later WebKit repeat showed it again. A temporary repro spec caught the console error: `Cannot read properties of null (reading 'items')`. A new search aborts the list request still in flight. When the abort landed after the headers but during `res.json()`, `api()` caught the AbortError, called it "no body", and resolved the cancelled request with `null`. The list then read `null.items`. This code dates from P1. `api()` now rethrows an AbortError from the body read. `tests/unit/api-client.test.ts` fails without the fix. Before: 3 of 18 repro runs crashed. After: 24 of 24 runs, 144 searches, no error. `docs/evidence/P8.1/search-render-error.txt`.

## Timed run

The automated run of all five steps, recap and reset takes seconds in the browser, and the recap shows a server-timed duration from launch to the last step on every run. That proves the path works end to end. It doesn't prove a person finishes in five minutes. **P8-A's human half is pending a person**: one first-time visitor, timed, with the script in `docs/DEMO-SCRIPT.md`, recorded here.
