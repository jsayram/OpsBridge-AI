**Failures on the way:** three isolation tests failed because the seed gave an owner case the same UUID as a template case. The database showed the guest was reading the template row, and no owner data was exposed. Owner rows now have their own IDs, with a test. While writing tests, I found the runtime role could write the template if a bug set it as the current workspace. `app.writable_workspace()` closes that. The first mutation log for M5 misread a real regression as a side effect, corrected in `mutation-canaries-run1.txt`. A later rerun produced empty sections because of a shell quoting mistake, and the committed log is the proper rerun.

Not verified: Hyperdrive transaction behavior (ADR proofs 2, 3), load, and the lock timeouts under real contention.

## Security, quality and cost

- Stacked locks: scoped query, RLS, composite foreign keys, no runtime rights on session tables.
- A stolen cookie works until expiry or reset, for synthetic data.
- Many networks together can still fill the 150 cap. The cap and retention hold, and visitors see a clear message with the walkthrough.

## Decisions, teaching notes and approvals

**Teach-back.** A visitor gets a long random token in a cookie that page scripts can't read, and the database keeps only its fingerprint. Every query names the workspace, and the database refuses other rows even if a query forgets to. We tested that by removing the query filter on purpose: guests stayed apart. Reset builds a new workspace and marks the old one expired, so no public request can delete anything.
