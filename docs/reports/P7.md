## What P7 changed in the app

- **The outbox dispatcher has its own database role** (`opsbridge_dispatcher`, D-076), closing D-061. The request role can no longer claim or finish an outbox event. Hosting now needs a third Hyperdrive config, and the release config gate refuses a deploy without it.
- The change is split into `0010` (expand) and `0011` (contract) so a rollback to the P6 Worker keeps dispatching. The rollback rehearsal caught that the first version broke this rule. `db.mjs migrate --to` lets a host ship them a release apart.
- The report page binds its `LIMIT` and `OFFSET`.
- Everything else is tests, scripts, runbooks and documents.

## Release readiness: what Jose must do

### Before staging (unblocks P1-E, the hosted half of P7-C, P7-D on real devices, and P8.4)

1. Create the free Cloudflare and Neon accounts himself (DEC-002), following `docs/runbooks/HOSTED-SETUP.md`. In Neon: Postgres 17, compute capped at 0.25 CU, a `staging` branch.
2. Run `infra/db/bootstrap-roles.sql` on the staging branch. It now creates four roles. Give each a long generated password in a password manager.
3. Create **three** Hyperdrive configs with caching off: app, cleanup and dispatcher. Send the master the IDs, which aren't secret.
4. Set the Worker secrets and variables in `docs/ENVIRONMENTS.md`, including `IP_HASH_KEY` and `OWNER_SUBJECT_ALLOWLIST`.
5. Decide whether to set up Cloudflare Access now (owner sign-in, `docs/runbooks/IDENTITY.md`) or keep admin paths answering 404 for the first staging deploy.
6. Approve the staging deploy. The session then runs the release in `docs/runbooks/RELEASE-ROLLBACK.md`. On this first deploy the database is empty and no older Worker exists, so every migration, `0011` included, can go at once. From then on a contract migration waits one release.
7. After it's up, approve the hosted rehearsals: smoke, the negative sweep against staging, a Neon point-in-time restore into a branch, `wrangler rollback`, Workers CPU per request on the analytics overview and report routes, Neon wake-up timing.

### Before a public launch

8. Open the staging URL in real Safari on a Mac and on an iPhone and run the guided demo, including **New case** right after the case list loads (the one unexplained WebKit intermittent).
9. Do a VoiceOver pass, or have someone do it, on the guided demo, `/app/analytics`, `/app/reports` and `/app/roi`, and record who ran it (P6-E).
10. Choose a license for the public repository, or decide to state "all rights reserved".
11. Turn on GitHub private vulnerability reporting and put the channel in `SECURITY.md`.
12. Optionally add CodeQL in CI (free on a public repository) and WebKit to CI (roughly doubles the browser step).
13. Decide the demo capacity policy (cap 150, purge 5 every 30 minutes) after the Workers CPU measurement.
14. Read and approve the P8 case study and video before anything is published.
15. Live integrations stay optional and Pending Owner Credentials: a Salesforce Developer Edition org (P3-D), a Google Sheet and Zap (P4-C), an AI provider with a hard budget (P5.3). The public demo works without them.
